# Payment Automation Architecture (MX/LATAM)

Objective: fully automate payment-to-provisioning with safe exceptions only.

## Provider strategy
- Primary: Stripe (cards, subscriptions, webhooks, broad SDK support).
- Secondary/Fallback (MX): OpenPay or Conekta when local processing constraints require it.
- Optional wallets/alt-pay: Mercado Pago / PayPal according to target segment.
- Rule: one active primary per environment, fallback only after explicit switch policy.

## Fastest collection matrix (recommended)
1. Instant checkout link (card + wallet): default for all inbound leads.
2. Bank transfer rails (SPEI/CLABE): for B2B ops teams and invoice-oriented buyers.
3. Cash-reference payment (OXXO/retail voucher): for non-card users.
4. Manual cash intake (offline): allowed only with same-day internal registration and signed receipt.

Priority policy:
- Consumer/non-IT: card + wallet + cash-reference visible by default.
- B2B/ops: card + transfer visible by default.
- High intent: prefilled checkout link sent immediately after qualification.

Operational override (FacturAutentica Phase 1):
- Show PayPal + card first.
- Transfer stays as immediate fallback for invoice-oriented buyers.

## Cash handling policy (strict)
- Cash is accepted only through controlled modes:
  - provider cash-reference vouchers (recommended)
  - manual cash intake with evidence and same-day digital registration
- No provisioning without digital payment record in billing state.
- Mandatory controls for manual cash:
  - unique paymentId generated at intake
  - receipt photo/PDF attached to payment record
  - operator ID and timestamp logged
  - dual confirmation before mark-succeeded

## Mandatory flow
1. Lead receives checkout link generated by commercial policy.
2. Customer pays in provider checkout.
3. Provider sends signed webhook to backend.
4. Backend verifies signature and idempotency key.
5. Backend emits payment.succeeded event.
6. Provision account/use-case runs automatically.
7. Runtime state + funnel metrics update.
8. Customer receives confirmation and onboarding trigger.

## Required backend endpoints
- POST /api/billing/webhooks/provider
- POST /api/billing/checkout/session
- GET /api/billing/checkout/status/:sessionId
- POST /api/billing/manual-cash/register
- POST /api/billing/manual-cash/confirm

## Security controls (required)
- Signature verification on every webhook.
- Strict idempotency for paymentId/eventId.
- Replay attack window limit.
- Secret rotation policy (90 days max).
- PII minimization in logs.
- Alerting on failed signature spikes.
- Role-based permission for manual-cash confirmation.
- Daily reconciliation between provider settlements and runtime payment records.

## Data contracts
- payment.succeeded payload must include:
  - paymentId
  - customerId
  - productId
  - planId
  - amount
  - currency
- account.provisioned payload must include:
  - accountId
  - customerId
  - productId
  - planId

## Human gates in this architecture
1. Approve discount policy changes.
2. Approve contract exceptions out of policy.
3. Approve publication/go-live by channel.
4. Approve manual-cash exceptions above threshold.

## No-human default decisions
- send_checkout for high-intent and high-value when policy allows.
- request_payment_method on invoice block.
- auto-provision on confirmed succeeded payment.
- auto-close with fastest available payment rail per segment.
